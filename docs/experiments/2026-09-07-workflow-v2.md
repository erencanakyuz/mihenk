# Qwen 20-account workflow revision

Current default: `--workflow=v2` now uses `toolChoice: auto`; a participant may return without choosing an operation. Compact memory, bounded views, permissions, and the 1,536-token output limit remain unchanged. The treatment below documents the completed historical run with forced `single` selection. Use `--tool-choice=single` only to explicitly reproduce that selection condition. See [the short follow-up comparison](2026-09-07-qwen-auto-choice.md).

## Question and baseline

Can the same 20-account crisis scenario produce reliable observable actions when the transport, account memory, and available target surface are corrected? The baseline is real model run `45336a97-9184-4fc9-bb4a-60838a42ab3a`, not the earlier scripted run. It completed 400 requests but produced 185 unpublished comments, 55 truncated outputs, 9 format errors, and 273 requests that dropped history. Only 116 mutations were committed.

The baseline also contains substantive decision failures: Derya was banned, Cem remained active, Merve addressed Hasan's insulin need while targeting Derya, and Nadir closed a request before recorded delivery. Infrastructure corrections must not silently label these decisions as correct or supply scenario answers to participants.

## Treatment

- `historyMode: compact`: account-local receipts replace repeated copies of complete screens. Historical public cards and messages remain separately bounded and explicitly historical. Current observations appear once. Recordings retain the original complete observations and provider responses. A changed access revision clears both history and recalled content.
- `toolChoice: single`: one named `account_step` function returns exactly one operation/arguments object. Its schema contains only the currently available operations and targets, including reading or waiting. It does not require publication or moderation. The old `auto` and provider-native `required` options remain available. This changes the experiment: an increased action count alone is not evidence of increased spontaneous initiative.
- Fresh mutation targets: only the current permitted view supplies actionable targets. Previously observed IDs support navigation, not stale mutation permissions. Target schemas distinguish account IDs from post IDs. The server still checks authorization, seen targets, state, and version at execution; simultaneous actors can still race.
- Personal context: a bounded view of the account's own active requests remains available across feed filters. No truth labels or private facts about other actors are added.
- Bounded screens: six thread messages, two related posts, and four updates are supplied at a time; repeated cards/messages are deduplicated. `open_thread.offset` and `nextMessageOffset` expose older message pages. If exact tokenization still exceeds the input limit after recall/history reduction, the controller reads a smaller real page and rebuilds its action targets before inference. Each reduction is recorded. Other accounts' view settings are independent.
- Output limits: the ceiling is 1,536 tokens so a complete single operation can fit. A cut-off output or missing required operation is a recorded error with no mutation, never an intentional abstention or a successful action.
- Reply authors: an account visible through a reply or offer can be targeted under the same access, self, and protected-account rules as a post author. Seeing a reply must not silently omit a moderator's account operation.
- Repeatable starting world: the operator can create a new run from another run's pristine initial state. Initial seed IDs, timestamps, feed tie ordering, and scheduled events are preserved. Accounts, sessions, histories, and later generated content are new.

The v2 role prompts are identical to the baseline. There is no Derya exemption, Cem ban instruction, hidden truth lookup, fabricated delivery, or automatic conversion of prose into published posts. Raw model output is distinct from a successful server receipt.

## Run and interpret

Start the local rehearsal server and the configured Qwen endpoint, then:

```powershell
node lab/run-adversarial-20.mjs --workflow=v2 --source-run=45336a97-9184-4fc9-bb4a-60838a42ab3a --endpoint=http://127.0.0.1:8000 --model=Qwen/Qwen3.5-9B --revision=c202236235762e1c871ad0ccb60c8ee5ba337b9a --tool-argument-encoding=qwen3_xml
```

The source run must exist in that server's database. Omit `--source-run` for a newly generated scenario. `--workflow=baseline --tool-choice=auto` restores the original memory/response configuration; the current product permission and target fixes remain applied. A historical binary comparison requires the recorded source version as well.

Keep model revision, role prompts, 20 independent accounts, 10 concurrent requests, 20 decisions per account, 12,288 input tokens, temperature 0.7, top-p 0.8, and thinking off unchanged. The output ceiling changes from 768 to 1,536; the view limits and single-object transport are part of the treatment. The runtime remains one Qwen replica shared by 20 accounts on the A100 40 GB.

Compare coverage, request/response identity, real mutations, rejected actions, valid reads/waits, format errors, truncation, receipt retention, recalled-context trimming, token cost, duration, and latency. Then inspect moderation targets, aid target matching, duplicate requests, unsupported claims, and premature completion against event evidence. This is one bundled workflow comparison, not a causal attribution to an individual change or an intelligence score.

## Intermediate run and root-cause evidence

Run `418e3e6e-bd0f-4758-80af-30df4313503d` is retained as an incomplete attempt: all 20 accounts responded, with 94 requests/responses, 732,049 charged tokens and 140 seconds. It stopped at `input_budget`: the current screen plus tools alone reached 13,784 tokens. Eight requests trimmed historical recall; the final over-budget decision also exhausted its three receipt entries without fitting. The initial memory fix therefore did not solve an oversized current conversation.

Nine provider outputs were cut off. A replay of the first failing request at a doubled 1,536-token limit still failed. Decoding its generated token IDs showed a growing array of separate reply operations despite `parallel_tool_calls:false`; the parser returned an empty tool-call list because that array never closed. Those empty outputs were initially recorded as comments; analysis must distinguish them from deliberate no-action choices.

Replacing that transport with a named, single-object schema on the same failing example produced one complete call in 1.34 seconds and 46 output tokens. This was a transport probe and was not executed against the world. No GPU model dependency was patched; the correction is in the provider-independent adapter. The second complete-run attempt uses the corrected schema and paginated views.

vLLM's [tool-calling documentation](https://docs.vllm.ai/en/stable/features/tool_calling/) documents named-function and `required` structured output. The installed runtime's observed array behavior is the reason for choosing the named single-object form here.
